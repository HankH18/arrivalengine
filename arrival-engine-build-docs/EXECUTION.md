# Execution Notes (for the orchestrator)

Doc set: `SPEC.md` (intent) → `DESIGN.md` (contracts) → `TASKS.md` (ten tickets). Read this file, then `TASKS.md`'s dependency graph; load `SPEC.md`/`DESIGN.md` sections only as a ticket's `Refs` names them.

1. Work the graph, not the doc: pull ONE ready ticket (all `Depends on` closed), load only its contract, the DESIGN sections it references, and the files in its `Scope`/`Reads`. Do not load the full task graph or other tickets' contracts.
2. A ticket is closed only by its `Verify` command passing. No model judgment substitutes for a passing check. Before dispatching a ticket, run its `Verify` in a worktree without the ticket's work and confirm it fails; if it passes, the ticket has no gate — stop and fix the ticket, not the code. T-0 is the sole `bootstrap: true` exemption.
3. Parallelize only tickets whose `Scope` globs are disjoint from every open ticket (after T-0: T-1, T-2, T-3, T-4, T-5). Everything else serializes in dependency order. Dispatch on per-file ownership, not on the advisory flag.
4. Shared primitives live in `src/arrival/contracts.py` and `src/arrival/util.py` (T-0). A ticket that finds itself writing a slug, whitespace-normaliser, hash, or a model that already exists in contracts must import it instead — if the contract is wrong, escalate (item 6); do not fork it.
5. On failure: revert to the ticket's starting state before retrying — do not iterate on top of a failed attempt. After two failures on one ticket, stop and escalate.
6. On discovered reality (a source is dead, a quota changed, a contract is unimplementable, a taste fixture is wrong): stop, rewrite the un-started tail of the graph with the strongest available model, then resume. Never push through a stale plan. Decisions tagged `[reasoned — not executed]` in DESIGN (notably Decision 10, the `--ticket` selector) must be executed by the first ticket that uses them (T-0) before being trusted anywhere else.
7. Escalation: done-ness disputes, repeated failures, re-planning, anything touching the taste line (R11) or the resolver's strong-key rule (Decision 4), and the human approvals (taste fixture in T-4, dossier review in T-9) go to the strongest model or the human owner — never to the executing model.
8. Time: the budget is ~14 h against ~16.5 h of estimates. Apply `TASKS.md` §Cut list in order when behind; never cut the "never cut" items. Log hours per ticket by appending one line to `HOURS.md` as you close it — the client scores the hour count. `HOURS.md` is append-only and exempt from per-file ownership checks; every other file is owned by exactly one open ticket at a time.
